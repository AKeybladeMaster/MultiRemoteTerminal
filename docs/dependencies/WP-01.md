# WP-01 dependency review: local terminal

**Reviewed:** 2026-10-23. These are the new direct runtime dependencies selected for the Windows local-shell slice.

| Package | Pin | License | npm unpacked size | Decision |
|---|---:|---|---:|---|
| `node-pty` | 1.1.0 | MIT | 64,363,742 bytes | ConPTY-backed pseudoterminal adapter; upstream supports Windows ConPTY on Windows 10 1809 and later. The project uses only the allowlisted PowerShell and cmd executables. |
| `@xterm/xterm` | 6.0.0 | MIT | 5,921,599 bytes | Terminal emulator in the sandboxed renderer; consumes validated output events and sends typed input/resize requests through preload. |
| `@xterm/addon-fit` | 0.11.0 | MIT | 20,727 bytes | Fits the terminal grid to its host element and reports changes through the typed resize command. |

The pins are exact in `apps/desktop/package.json` and the lockfile. `node-pty` uses Node-API; Node-API's ABI stability made an Electron-specific rebuild package unnecessary for this slice. The pinned prebuilt module was loaded and exercised from an Electron 45 utility process in the Windows acceptance test. This verifies the tested x64 development runtime; it does not replace a packaged-app smoke test or a signed release inventory.

`pnpm-workspace.yaml` explicitly allows the `node-pty` lifecycle scripts. Its install step selects the native prebuild and stages the ConPTY support DLL. No other package receives lifecycle-script permission for this change. `pnpm audit --prod` reported no known advisories on the reviewed lockfile.

The runtime explicitly selects Windows-provided ConPTY (`useConpty: true`, `useConptyDll: false`). A nine-shell Windows resize check exposed stale PowerShell window dimensions with the optional bundled-DLL path; the system-ConPTY path passed three repeated checks and the full Windows E2E. See [ADR-0004](../adr/ADR-0004-system-conpty-for-local-terminals.md). This is Windows 11 x64 evidence only.

WP-01E adds optional Bash through an existing Git for Windows installation; the application does not bundle or redistribute Git for Windows and adds no package dependency.

| Provider record field | Git for Windows Bash |
|---|---|
| Name and source | Git for Windows Bash; user-installed from the [official Git for Windows project](https://gitforwindows.org/) |
| Version | The acceptance machine had `2.53.0.windows.2` (`bash.exe` file metadata) on 2026-10-24; versions vary because the user manages this installation |
| License | Git for Windows distributes Git under GPL-2.0 and includes components under compatible or other listed licenses; review the installation's release notes and component notices for the exact bundle. This application does not redistribute any component. See the [official FAQ license section](https://gitforwindows.org/faq). |

| Hash/signature check | The resolver verifies only that the expected file exists under a standard Git root; it does not enforce Authenticode or a pinned hash. On the acceptance machine, Windows verified the `bash.exe` Authenticode signature as valid. This machine-specific observation is not app enforcement. |
| Update policy | User-managed through the Git for Windows installer/updater. The app does not download or update it; use current official releases and security notices. |
| Vulnerability status | The app does not scan or pin the external installation. The acceptance runtime was `2.53.0.windows.2`; the official FAQ currently recommends upgrading versions older than `2.56.0(3)` because earlier releases include security fixes. Treat the local runtime as requiring a user-managed update before relying on it for sensitive work. See the [official Git for Windows FAQ](https://gitforwindows.org/faq). |

The resolver checks standard machine and per-user install roots for `<Git>\\bin\\bash.exe`, the Git for Windows wrapper that configures its runtime before launching Bash. It intentionally ignores `System32\\bash.exe`, which is a WSL launcher, and does not search arbitrary PATH entries. Custom install roots and WSL integration remain unsupported. See the [official wrapper documentation](https://gitforwindows.org/git-wrapper.html).

The `New Bash terminal` command and opening a saved Bash session are explicit user actions. The wrapper starts Bash with `--login -i`, so Bash loads its normal user startup files under the Windows account. This is Bash's selected-shell behavior; the application does not configure or automatically run an app-managed profile script. Any future app-managed startup script must follow the preview/explicit-enable policy in `SECURITY.md`.

The node-pty npm artifact is relatively large because it ships native builds and ConPTY support. Distribution packaging must measure the actual Windows x64 output and account for the bundled DLLs. Keep `node-pty` in the utility worker; do not load it from the renderer or main-process UI code.
