# ADR-0026: Opt-in read-only loopback TFTP server

**Status:** Accepted for partial WP-10A implementation; broader acceptance remains open (2026-10-26)

## Context

F-022 calls for optional local daemons and P-20 requires controlled server lifecycle. TFTP has no authentication, so a running service can expose files to local processes. The service must not start at application launch, listen beyond loopback, accept uploads or let renderer code choose arbitrary filesystem paths. TFTP also assigns transfer identifiers (UDP ports) that remain fixed for the duration of a transfer; see [RFC 1350, section 4](https://www.rfc-editor.org/rfc/rfc1350.html#section-4).

## Decision

- Require a native folder selection and explicit Start action. Display a clear warning that TFTP has no authentication and any local process can read top-level files in that folder while the server is running. Stop is explicit; renderer loss/crash and application shutdown also close the worker.
- Bind the listener and each transfer socket only to IPv4 loopback (`127.0.0.1`). The listener defaults to UDP 69; port 0 permits the OS to choose an available port. Do not add an automatic Windows Firewall rule.
- Implement RRQ in octet mode only. Decode the request filename as strict UTF-8; accept Windows-legal single path components up to 255 UTF-16 code units, with the complete request bounded to 1,024 bytes. Reject malformed UTF-8, WRQ, subdirectory paths, traversal, invalid Windows filename characters, reserved device names, symlinks/reparse points, non-regular files and files over 16 MiB. Ignore well-formed optional request fields without negotiating unsupported extensions. Reply with TFTP ERROR 5 to a packet from an unexpected transfer ID without disturbing the active transfer; return ERROR 4 and terminate for malformed transfer packets from the expected peer.
- Send errors that reject an initial request from a separately bound loopback transfer ID. Cap simultaneous error-response sockets at eight and close them on completion, timeout or service stop; clients must receive the server's chosen transfer ID in the reply.
- Keep filesystem access in a supervised Electron utility worker. Main stores the selected absolute path behind an opaque token; typed IPC carries only that token, a validated port and status. Renderer code never receives the path or opens a network socket.
- Bound service work to eight active and eight pending transfers, a 120-second transfer deadline, 512-byte blocks, three retries at one-second intervals and worker-owned cleanup on stop/exit. Add no arbitrary total runtime timeout.
- Do not add a third-party protocol package; use the pinned Node runtime's `node:dgram` and filesystem APIs.

## Consequences and limits

The server is unauthenticated and intentionally exposes every permitted top-level file to local processes while running. It has no write path, subdirectory browsing or network-interface selection. UTF-8 is the documented encoding for RRQ filename bytes in this Windows provider; the parser rejects invalid UTF-8 and enforces Windows component rules while supporting Unicode and names beyond the earlier 120-character limit. A Windows UDP integration test verifies exact-byte transfer of a long Unicode filename. The expanded Windows E2E passed three consecutive runs with exact-byte RRQ, 16 MiB ceiling rejection, eight active requests plus one bounded busy response, loopback transfer-ID checks, active stop, port release, restart and shutdown. Its opt-in long-runtime run kept TFTP running beyond 360 seconds, then completed a transfer and explicit stop; P-41 is verified for this TFTP provider. A mixed-load worker UDP test keeps seven transfers active while eight file opens are pending, rejects request nine, then confirms only one pending transfer enters the final active slot and seven receive busy responses. This validates both pending admission and the active-transfer cap across asynchronous opens, not general packet-storm behavior. The test account cannot create a file symlink (EPERM), leaving runtime symlink rejection open despite the worker's lstat guard. The earlier ACK timeout remains historical evidence, is not currently reproducible, and has no established cause. Effective Windows Firewall policy blocks inbound traffic and dropped-packet logging is disabled, so the firewall's role in that earlier failure is unknown. The loopback-only bind and RFC transfer-ID behavior remain required. Broader interoperability, machine-to-machine exposure/isolation and NFS/Cron/helper daemons remain unverified; P-20/F-022 stay partial.

## Verification

See [WP-10A results](../results/WP-10A-loopback-tftp-2026-10-26.md). Static checks, focused unit tests, exact-byte transfer including a long UTF-8 filename, >360-second TFTP service lifetime, runtime WRQ/traversal and oversized-file rejection, active and pending admission caps, loopback transfer-ID checks, active-transfer stop, renderer-crash cleanup and application-shutdown cleanup pass. Runtime symlink rejection remains unverified; the current Windows account cannot create a symlink. Broader interoperability, machine-to-machine exposure/isolation and NFS/Cron/helper daemons remain open.
