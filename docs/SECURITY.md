# Security Architecture and Test Checklist

**Threat model:** Desktop application executes local commands and communicates with untrusted network servers. Remote terminal output, file names, user-supplied profile scripts, third-party viewer processes and network peers must be treated as untrusted. User is assumed to control their Windows login; the app must protect against accidental exposure, compromised servers, malformed inputs, malicious downloads and privilege boundary violations. Protection against fully compromised same-user malware is out of scope.

## Core threats and mandatory controls

|---|---|---|---|

| Command injection | Untrusted host/path interpolated into shell | Structured provider args and APIs, `spawn` without shell, no command concatenation | Host/path with quotes and metacharacters has no side effect |
| MITM via host key | New/changed SSH host silently accepted | Strict trust-on-first-use approval with fingerprint; changed keys BLOCK, explicit trust reset | Fixture replaces key; connection stopped |
| Vault disclosure | Secrets in SQLite/logs/UI | Vault encryption, reference IDs, no renderer secret reads, redacted structured logs | Scan DB/logs; review IPC traces |

WP-06B1's Windows E2E verifies a password prompt already open at recording start, recognized PowerShell password and verification-code prompts, paste omission and paused resume behavior; unit tests cover prompt latching, ANSI controls and cursor-addressed redraws. Detection and redraw classification remain heuristic; arbitrary secrets or prompt styles may not be recognized. No terminal transcript is persisted. |
| MultiExec command fanout | A user submits sensitive or unintended text to the wrong terminals, or one failure hides delivery to other targets | Warn that text executes immediately and should not contain secrets; reject control/bidi formatting and Unicode line separators; show exact text and each selected destination; require final explicit approval; cap target count and concurrent writes; report each target separately; never retry or substitute targets; report timeouts as uncertain; cancellation stops queued writes; capture no output and persist/log no command text or target list | Windows E2E reviews exact text and sends once to three distinct loopback SSH hosts with separate host keys, ports and input recorders; unit tests cover approval, target validation, isolated failure, no retries, uncertain timeout and cancellation. |
| Third-party supply chain | Untrusted binary/provider injection | Signed/pinned installer deps, license inventory, hash/provenance and opt-in tools | SBOM + allowed binary provenance |
| Unexpected daemon exposure | User starts public listener unknowingly | Loopback default, UI display bind/port, require explicit approval, firewall notes; WP-10A TFTP binds only to 127.0.0.1 and requires an explicit folder selection and start action | TFTP E2E verifies exact-byte transfer, >360-second service lifetime, oversized-file rejection, eight active RRQs with a bounded ninth-request error, WRQ/traversal denial, active-transfer stop and restart/shutdown cleanup. | Unlimited resource exhaustion | Thousands of sessions create open handles | Unlimited *definitions*, resource-based runtime throttling and queue backpressure | 1,000 persisted, graceful saturation |
| Worker crash & leak | SSH/PTY crashes leaving sockets | Supervisor closes owned streams and listeners, clears secrets, updates status | Kill worker scenario |

## Electron minimum configuration

- Current patched Electron version; renderer `sandbox=true`, `contextIsolation=true`, `nodeIntegration=false`, secure custom app protocol, `webSecurity=true`.
- Windows release builds apply all Electron v1 fuses with `strictlyRequireAllFuses`: disable `RunAsNode`, Node environment options, inspector arguments and extra `file://` privileges; enable cookie encryption, embedded ASAR integrity and ASAR-only app loading; keep Wasm trap handlers enabled and the unused browser-specific V8 snapshot disabled. The Windows package smoke reads back every fuse and launches both artifacts; see [WP-07G](results/WP-07G-electron-fuses-2026-10-25.md).
- Deny unnecessary permissions and navigation. The only current permission exception is `clipboard-sanitized-write` for the trusted `mrt://app` main frame; clipboard reads from the renderer, subframes and all other origins remain denied. Copy selection writes only after the explicit terminal-tab action. Ctrl+V and Ctrl+Shift+V require a one-use native keyboard gesture and a matching trusted key event from the focused terminal; the main broker reads clipboard text and never returns it to the renderer. It rejects NUL-containing text and text longer than 16,384 characters before sending it to a session. Electron materializes the clipboard string in main before this length check, so the cap bounds terminal input, not the initial clipboard read. Terminal input is queued in order per session, including across the asynchronous paste authorization step. Multiline text requires a native confirmation because writing raw lines can run multiple shell commands; the paste request waits for the user's decision, and renderer teardown cancels it before any write. External URL access requires allowlisting.
- Strict CSP; no unsafe-eval or arbitrary HTML/JS rendering of terminal output. `style-src` permits inline styles because xterm installs runtime styles for ANSI colors and terminal decorations. `img-src` permits `data:` only for bounded, normalized PNG workbench logos; scripts remain `'self'` only, and network, object, frame and form sources remain denied. The main process persists a changed logo only when it matches the exact normalized value returned by its bounded picker. Keep output as text, and preserve the CSP tests for image-only data URLs, inline script and network denial.
- A loopback SSH E2E sends terminal output containing an HTML event handler that attempts to write a file through Node. It verifies the payload remains text, creates no DOM image, exposes no `process`/`require`, executes no marker, and writes no file; see [WP-07I](results/WP-07I-hostile-ssh-output-2026-10-25.md).
- WP-01G shell coloring is opt-in and reads only the current text already present in xterm's parsed screen buffer after an explicit keystroke at a recognized prompt. It adds transient decorations, sends no extra IPC, changes no terminal bytes, and stores or logs no command text. A shell may suppress echo for secret input; this feature does not inspect hidden input or attempt to classify commands as safe.
- WP-01I builtin and wrapper coloring is a fixed lexical hint. It does not inspect installed shells, PATH, aliases or functions; it neither changes nor evaluates terminal input. The current input/row/decoration bounds and opt-in preference continue to apply.
- WP-01J carries only bounded Shell tokenizer flags across an unquoted backslash continuation. It stores no submitted command text, logs no syntax state and clears the flags on completion, cancellation, failed input, disable or pane teardown. Continuation coloring remains opt-in and uses a visible `>` prompt suffix as a heuristic; a custom primary prompt with the same suffix is ambiguous.
- WP-01K/WP-01L/WP-01M route active input from the common `PS <path>>` prompt through the existing bounded PowerShell tokenizer and carry only its small command-position state across an unquoted odd trailing backtick or recognized trailing pipeline, binary, assignment, logical or array-separator operator to an exact `>>` prompt when the caret is at an unambiguous logical input end. At xterm's occupied final-column wrap-pending position, the public buffer API cannot resolve the caret side, so state is withheld. The renderer reads only xterm parsed normal-buffer input after explicit typing, adds transient decorations, and does not retain, log, persist or send command text for highlighting. Visible prompt text means custom prompts matching the same primary or secondary forms also match; unlisted continuation forms are not detected or parsed. The same opt-in setting and input/row/decoration bounds apply.
- Validate IPC origin/sender and schemas for **every** command; do not expose raw `ipcRenderer` from preload.
- Main or privileged worker owns filesystem, system processes and vault. Distinguish worker process isolation from a strong OS sandbox.
- Review Electron security guidance before first release: https://www.electronjs.org/docs/latest/tutorial/security/
- Packaged acceptance mutates the SHA-256 integrity metadata inside an installed `resources/app.asar` and verifies that the application process exits. Test-only delay hooks require an unpackaged build, `MRT_E2E=1`, and their exact command-line flag; the focused unit test also proves packaged builds ignore them. See [WP-07H](results/WP-07H-n002-electron-review-follow-up-2026-10-25.md) and the official [ASAR integrity guide](https://www.electronjs.org/docs/latest/tutorial/asar-integrity).

## SSH rules

- Host authenticity verified on initial connection, reconnection, jump-host chain and SFTP/tunnels. No default `hostVerifier:()=>true`.
- Default key-exchange, cipher and MAC list from well-maintained library; disable deprecated algorithms unless user explicitly opts in with visible warning and scoped host override.
- Password/key/agent auth; no persistent passphrase in plaintext. Agent forwarding disabled by default.
- WP-02A implements direct SSH terminal and standalone SFTP private-key auth. The native main-process picker is the only key-file source; main accepts a regular file up to 1 MiB, and key bytes stay out of renderer IPC, profiles and logs. Username and optional passphrase use the protected Windows prompt. Transient key buffers are zeroed after use. Windows loopback E2E covers encrypted Ed25519 authentication for both an SSH terminal and standalone SFTP files-only listing; packaged native prompting remains unverified. WP-02B's same-library mock covers agent signing for an SSH terminal and a standalone SFTP files-only listing. WP-04I adds mock-agent signing at SSH terminal and SFTP destinations through three password-authenticated gateway hops. The application port carries only the agent method and username; the Windows named-pipe endpoint is configured on the supervised SSH worker. Actual Windows OpenSSH service interoperability through gateways, disposable OpenSSH acceptance and broader interoperability remain open.
- Unknown host key requires fingerprint display and explicit approval. Mismatched key halts connection and provides a separate administrative reset action.
- WP-04D/WP-04E/WP-04F/WP-04H routes support up to three ordered saved gateways and send profile IDs through typed IPC; main resolves only saved SSH gateway definitions, while credentials stay in the main-to-worker connection flow. Every gateway and target must pass independent host verification. SFTP-only routes request the SFTP subsystem without a PTY or shell; gateway-routed tunnels use a files-only SSH runtime without a PTY, shell or SFTP subsystem. Routes are connection-scoped and are not saved or exported with profiles or tunnels. Windows loopback E2E verifies three-hop terminal, SFTP and tunnel routes and cleanup; longer routes and public-server interoperability remain open.
- Limit connection/login retry frequency and cancellation; do not log authentication payloads.
- WP-04C dynamic SSH forwarding exposes a no-auth SOCKS5 listener on `127.0.0.1` only and only after explicit start. Any local process able to reach loopback can use the authenticated SSH profile to request TCP CONNECT destinations that the SSH server permits; the UI identifies the port and explains that no proxy authentication is used. Each tunnel allows at most 64 pending/open connections and applies a 15-second handshake/channel-open deadline. UDP ASSOCIATE, BIND and authentication sub-negotiation are unsupported; unsupported requests fail closed. Stop, connection close, worker shutdown and app shutdown close both ends and release the local listener. Never expose the listener on a LAN address.
- High-risk operation output may be sensitive; no transcript logging by default.
- Installers/updates and downloaded tools use HTTPS and integrity validation.
- Contextual WP-05A/WP-05B browsing reuses a trusted, running SSH connection. Standalone WP-05C SFTP uses the same first-use host-trust and credential flow but authenticates without requesting a shell or PTY; the files-only mode rejects terminal input, resize and output acknowledgement. Saved SFTP profiles store only the canonical host and port, never credentials. Listing and transfer paths/replies are validated at the application, worker protocol and domain boundaries; directory results are capped at 500 entries. Symlink entries are visible but not navigable. Before transfer I/O and again before commit, workers compare the server's canonical `realpath` with the normalized requested path and `lstat` the final object, rejecting known symlink ancestors; path-based SFTP cannot eliminate a race if a hostile server swaps an ancestor between the check and its use. Upload sources and remote download sources reject symlinks; downloads also recheck remote metadata around streaming and compare transferred bytes with the advertised size when available. Local overwrite rejects symlink targets, while rename and skip do not follow a pre-existing selected symlink. Uploads stream to a random exclusive remote sibling and commit with SFTP v3 rename; rename-on-conflict keeps the requested name when free and chooses a copy name only after a confirmed collision. Explicit remote overwrite stages a backup and attempts rollback if the replacement fails. Downloads stream to a random sibling in the user-selected directory; new files commit with a no-replace hard link, while explicit overwrite verifies the selected file identity before rename. The local filesystem rename used for overwrite has a small identity-check race with another same-user process. Transfer progress is coalesced to at most one event per 100 ms per operation plus a final byte count. A committing progress phase prevents cancellation after the commit boundary; delayed commit notifications extend an already scheduled cancellation grace so commit/rollback can settle. Other cancellation and timeout paths attempt bounded cleanup. If SFTP upload cleanup fails, the worker retains the exact owned stage path under a digest of the canonical route, usernames and accepted host keys; on reconnect for that route, it retries cleanup before SFTP operations with bounded attempts, a TTL and generated-path validation. A forced worker termination or app restart loses these in-memory records, so a remote `.partial` file may remain; local staging may also remain if its worker is forcibly terminated. No filename is shell-interpolated. Unit tests cover validation, conflict behavior and cleanup; Windows loopback E2E covers contextual upload/download and standalone first-use trust, listing, download, saved-profile reopen and absence of a shell request. WP-05F verifies an exactly 1 KiB dropped file on SFTP and FTP, a 100 MiB SFTP download, and a 100 MiB FTP upload and download with size and SHA-256 checks; WP-05G adds a 100 MiB SFTP drop upload with size and SHA-256 verification. These checks do not measure throughput. WP-05H verifies that a reset during SFTP download removes the local staging file and target, then permits explicit reconnect and a SHA-256-verified retry. WP-05J persists the setting that controls the contextual SSH file pane; standalone files-only sessions remain available when it is disabled. WP-05K verifies interrupted SFTP upload cleanup and explicit retry only after reconnect to the same trusted route while the worker remains alive. WP-05L verifies FTP upload-stage cleanup and exact-byte retry only after reconnect to the same endpoint, TLS mode and username while its worker remains alive; worker termination or restart loses these in-memory records. FTP exposes no stable object identity in this cleanup path, so a concurrent smaller replacement at the recorded pathname can be deleted. Native Explorer gesture automation and broader SFTP server interoperability remain unverified. See [WP-05K evidence](results/WP-05K-sftp-upload-recovery-2026-10-26.md) and [WP-05L evidence](results/WP-05L-ftp-upload-recovery-2026-10-26.md). WP-05I verifies FTP download-side staging cleanup and explicit reconnect/retry; see [WP-05I evidence](results/WP-05I-ftp-download-recovery-2026-10-26.md) and [WP-05J evidence](results/WP-05J-configurable-sftp-side-pane-2026-10-26.md).
- WP-09C/09D FTP/FTPS stores only host, port and the explicit-TLS selection in a saved profile. Username and password are collected in the native Windows prompt and are not returned to the renderer, saved in the session catalog or included in saved-folder exports. FTP credentials, requested paths and server-returned names reject control characters before they can enter line-oriented protocol commands. The FTPS connection uses normal TLS certificate validation. Plain FTP visibly warns that account credentials and file contents are unencrypted; the preload and main broker each require a short-lived, one-use user gesture bound to the endpoint. The utility worker disables verbose protocol output, blocks PASV redirection to another host, caps active connections at 32 and bounds listing memory/entries. Non-overwrite uploads use standard argumentless STOU after changing to the requested CWD; the server selects the actual filename, which is validated and shown when complete. The in-progress server-selected file is visible to listing clients. The worker captures its path from the 125/150 reply before data flow and attempts DELE after a graceful user cancellation while the FTP control connection remains available; connection loss may leave remote residue. Explicit remote overwrite uses a staged backup/replace sequence, with a bounded two-minute settlement window when the one-hour worker deadline lands during commit; forced termination can leave the old target under `.backup` and the replacement under `.partial`. Downloads stage to a sibling local temporary file and commit without replacing an unapproved target. Explicit local overwrite compares the selected destination's file identity just before rename, but Windows filesystem rename has no compare-and-swap identity condition, leaving a small race for another local process to replace the destination between that check and rename. Upload source identity and byte count are checked before success is reported. Other cancellation/timeouts use bounded cleanup; forced worker termination can leave a local partial download. WP-09F verifies that FTPS rejects an untrusted certificate and protects FTP control commands, listings and uploads when a local E2E test CA is explicitly trusted. The test-only CA path is unavailable to packaged builds; public certificate chains, data-channel session reuse and broader server interoperability still need Windows acceptance.
- Telnet is inherently plaintext. The Telnet provider stores only a canonical host and port in profiles and leaves credentials to interactive terminal input rather than app storage. Before every connection, including saved-profile reopen, the visible warning dialog must be explicitly submitted by a trusted user event. The isolated preload binds that short-lived, one-use gesture to the displayed endpoint, and the main-process broker independently consumes a sender-, session- and purpose-bound authorization before opening TCP; a direct bridge/IPC command cannot skip the warning. The terminal/status label identifies Telnet as plaintext. The TCP worker has bounded input/output queues, bounded subnegotiation, suppresses duplicate option negotiation replies, and uses explicit connect/IPC deadlines. It closes sockets on cancellation, failure, worker crash and shutdown. This transport is not suitable for secrets or untrusted networks; no Telnet traffic is encrypted or transcript-logged by the app.

## Serial-device operations

- A serial port is enumerated only after the user opens the port picker, and a device is opened only after the user selects a listed COM path and settings and presses Connect. No shell commands are sent on open. The serial worker accepts only canonical `COM1`–`COM4095`; it never accepts filesystem paths or serial numbers. Manufacturer display metadata is bounded and strips control characters. Do not log serial input or output: both may contain commands or device data. Device output is untrusted UTF-8 text interpreted by xterm's terminal parser, never as HTML or renderer code. Serial paste uses the existing one-use renderer gesture and multiline confirmation, with a 1,024-character cap. The native bindings run in a supervised utility process, which is process isolation and not a strong OS sandbox. Port drivers and physical device behavior still require Windows hardware and signature review.

## Master-password threat model

OS-protected storage on Windows is encrypted using a user-context mechanism; same-user malware can often access it. WP-07S adds an optional master-password mode using the exact Argon2id 1.3 profile (opslimit 2, 64 MiB, 16-byte random salt and 32-byte key) and XChaCha20-Poly1305-IETF entry envelopes with authenticated version/profile/reference metadata. Password derivation runs in a one-shot Electron utility process with a timeout; the renderer receives no password or derived key. Mode conversion uses staged ciphertext and verifies every entry before atomic replacement. Master-password mode starts locked after restart, persists cooldowns after failed unlocks and has no password recovery or escrow. A lost password requires explicit reset and credential re-entry. Same-user malware may still read credentials while the app is unlocked, and this does not make the application a memory-isolation boundary. Test persistence across reinstall, OS-account changes and data restore. Both modes lock after 15 minutes without a validated user-initiated app command and on Windows session lock or suspend; already-authenticated SSH transports may remain connected after credentials have been discarded. Physical Windows lock/resume behavior remains unverified. See [ADR-0003](adr/ADR-0003-wp02-interim-identity-storage.md).

WP-07K's Windows E2E uses Electron's real `safeStorage` and confirms a synthetic `powerMonitor` lock-screen event blocks vault resolution until an explicit test-only unlock, then checks that the random secret is absent from `credentials.json`. WP-07L closes and restarts the app under the same temporary profile and verifies the actual Windows-protected vault can resolve the persisted secret; the secret is checked against the vault file before and after restart. WP-07R adds explicit save/replace/forget for SSH profile passwords and user-facing vault lock/unlock. Its Windows loopback E2E confirms a locked vault blocks saved-profile authentication without a fallback prompt, unlock permits saved-profile authentication without a new prompt, and the test canary is absent from renderer-visible output, SQLite rows, exports, app-profile files and application console. WP-07S verifies the Argon2id/XChaCha profile with known-answer/tamper tests and Windows E2E through the actual Electron KDF utility process: Windows-account conversion, locked state after app restart, prompted unlock, lock and explicit reset. Focused tests verify atomic conversion, cooldown persistence and SQLite reference cleanup while preserving saved definitions. WP-07T copies a master-password vault into a different `userData` directory under the same Windows account, verifies the restored app remains locked and blocks resolution, then confirms the expected test password unlocks and resolves the entry. This does not verify cross-account restore, DPAPI-mode migration or packaged native prompting. The injected prompt hook is restricted to unpackaged launches with `MRT_E2E=1` and its exact test flag. Physical Windows lock/resume, account changes, restore under DPAPI, plaintext exclusion for other protocol flows and privileged process memory remain open.

**Caveat from Electron docs:** `safeStorage` synchronous API is deprecated in current docs; use async variant when supported by the selected pinned release. Confirm this API at implementation time, not by guessing Electron version.

## Telemetry and logs

Default is **no external analytics or telemetry**. Diagnostic logs locally opt-in, expiring/rotating, capped; never include passwords, private keys, full terminal output, arbitrary executed commands, auth headers or complete remote file contents. Crash reports off by default or sanitized explicitly. Users can clear local logs, known-host approvals and session metadata independently.

The SQLite storage adapter exposes only static `{component, event, code}` failure events on the local `multi-remote-terminal.storage` diagnostics channel. No listener or persistent log writer is installed by default; a future opt-in logger must remain local, capped and redacted, and must not add paths, SQL, hostnames, request IDs or stored values.

The customizable startup greeting is user-supplied UI text stored in the versioned `workbench` settings row, limited to 512 Unicode code points and accepted control characters. React renders it as text; the app never evaluates it or forwards it to a shell. It is ordinary app configuration, not a credential or encrypted vault value.

Portable profile initialization failures write the static `{component: "main", event: "portable_profile_initialization_failed", code: "PORTABLE_PROFILE_INIT_FAILED"}` record to stderr; the exception and filesystem paths are omitted. The user receives a generic message with a recovery suggestion.

## Secrets and key provenance

- Sessions reference `credential_ref`; vault content remains outside session definitions.
- Automatic saving of opened session definitions is disabled by default. Enabling it is an explicit persisted user choice; the main-process broker checks that stored preference before accepting `session.remember`, even if renderer state is stale or forged. Only validated protocol settings (shell or canonical endpoint/serial options) enter the catalog; credentials, private keys, command text and terminal contents remain excluded. The catalog deduplicates by normalized protocol settings. Gateway-routed SSH sessions are skipped because their route is not part of the saved definition, and external RDP/VNC launches are skipped because the workbench cannot verify a connection.
- SSH agent authentication asks only for the account username and uses the fixed Windows OpenSSH named pipe; private-key bytes stay with the OS agent. Agent forwarding is explicitly disabled. Mock named-pipe E2Es cover signing for a terminal and standalone SFTP files-only session directly and through three gateways; the installed Windows OpenSSH service and gateway interoperability with that service remain unverified. See [WP-02B](results/WP-02B-ssh-agent-auth-2026-10-26.md) and [WP-04I](results/WP-04I-routed-ssh-agent-auth-2026-10-27.md). Never copy private-key files into the DB.
- Clipboard paste and remote text editing may contain secrets: do not silently record.
- Accept known host certificate authorities only after verified implementation of SSH certificate semantics; do not pretend simple fingerprints cover OpenSSH hashed host entries/CA policies.
- Never automatically parse arbitrary SSH configs with command substitutions.

Saved-folder bundle files are explicit user-selected imports/exports through Electron's native file dialogs. Version 6 exports exact folder and local/SSH/SFTP/Telnet/FTP/RDP/VNC/serial connection metadata schemas; version 5 remains accepted for local/SSH/SFTP/Telnet/FTP/RDP/VNC profiles, version 4 for local/SSH/SFTP/Telnet/FTP/RDP profiles, version 3 for local/SSH/SFTP/Telnet/FTP profiles, version 2 for local/SSH/Telnet/FTP profiles, and credential-free version 1 for local/SSH/Telnet profiles. All supported versions enforce a 16 MiB file limit and a 100,000-record limit; credentials, private keys and terminal history are rejected or absent. Export writes a temporary file and renames it into place. Import validates the complete file before a single SQLite transaction; any conflicting folder/session ID or uniqueness constraint rolls back the whole import. The bundle format does not encrypt data, so it contains host names, ports, shell choices, folder names and saved-session metadata. Serial profiles include the COM port path and baud/framing/flow-control settings, but exclude USB serial numbers and credentials. Users should store these bundles as they would other connection configuration.

RDP connections use only the explicit `rdp.launch` capability. Launch requires a fresh, one-shot trusted click on the RDP dialog's launch button; the preload binds that gesture to the canonical host and port, and the main broker consumes a sender-scoped authorization before starting a process. Direct bridge or broker calls without that authorization fail closed. Main resolves the fixed `mstsc.exe` under System32 and spawns it with validated target arguments and `shell: false`; the renderer cannot choose an executable or pass credentials. Saved profiles include only name, host, and port. The dialog warns that Windows handles authentication and that the app cannot verify a connected desktop. After the process starts, the Windows viewer owns its lifetime independently of the workbench.

VNC connections use a separate explicit `vnc.launch` capability and a fresh trusted click bound to the canonical host, port, renderer, and VNC viewer type. The main process resolves only `vncviewer.exe` under the OS-known Program Files directories, never searches `PATH`, passes a validated TigerVNC `host::port` argument array with `shell: false`, and removes ambient `VNC_USERNAME`/`VNC_PASSWORD` values from the child environment. VNC profile and bundle schemas reject credentials; authentication stays in the external viewer. The dialog explains that encryption depends on server settings, and the app reports only a successful process launch. TigerVNC is user-installed and not bundled; the current integration does not verify its signature or hash. See [WP-08B dependency record](dependencies/WP-08B-tigervnc.md).

## Remote SFTP text editing

Remote file contents enter the renderer only after the user chooses **Edit** on a regular SFTP file. Reads are strict UTF-8, reject NUL/binary content and are capped at 512 KiB; malformed UTF-8 is reported without returning partial text. A SHA-256 revision and remote metadata identity are checked before save and again immediately before commit. The worker writes a unique exclusive sibling, then backs up and renames the original only after the revision still matches. Cancellation is honored before the commit boundary; once the worker reports `committing`, the bounded worker cleanup window allows replacement or rollback to settle. Failed or interrupted rollback/cleanup can leave a hidden `.mrt-*.backup` or `.mrt-*.partial` file on the remote host. Path-based SFTP cannot prevent a hostile server from racing ancestor replacement between checks. File contents, drafts and revision hashes are not written to logs, saved sessions, macro history or export bundles. The renderer keeps a conflicting draft in memory and requires explicit reload or close confirmation. Local file editing and shared renderer-only syntax previews are documented separately below; autosave is not implemented.

## Local text editing

Local file contents enter the renderer only after the user selects a file through the native open-file dialog. The main process retains the selected absolute path in memory behind an opaque UUID; renderer commands accept only that handle, and the renderer has no Node.js or filesystem access. Reads and writes run in a one-shot Electron utility process, which provides process isolation but is not an OS sandbox. The worker accepts regular files with strict UTF-8, rejects NUL and malformed input, and caps encoded content at 512 KiB. It checks file identity and a SHA-256 revision before saving, stages a sibling file, rechecks the source, moves it to a backup, then installs the replacement without replacing a path created concurrently. The UI retains the draft on a conflict and requires explicit user action to save, reload or discard. Mixed line endings are normalized to the first observed style and this is disclosed in the editor before save. Renderer-only Markdown/Shell/PowerShell/Python/JavaScript/TypeScript/SQL/TOML/YAML/JSON syntax previews treat content as text, change no file bytes, do not validate, render or execute it, and scan at most 64,000 UTF-16 code units and 4,096 tokens per refresh. Markdown is a bounded CommonMark-oriented subset with 512-code-unit per-construct inline lookahead and a 256,000-step aggregate lookahead budget; exhaustion shows the existing truncation notice. It does not render documents or track nested block containers. TOML uses ASCII-oriented bare-key classification. YAML uses a 1,024 UTF-16 code-unit implicit-key lookahead and simple indentation tracking for opaque block scalar text. These are bounded lexical aids, not parsers or validators. File paths, file contents, drafts and revisions are not persisted or logged by this feature. Selection handles are cleared on close or application shutdown, and shutdown waits for worker cleanup. Forced worker termination during replacement can leave a `.mrt-*.partial` or `.mrt-*.backup` file for manual recovery. Same-directory hard-link support is required for no-replace commit/restore; Windows ACL preservation after replacement is unverified. The E2E test uses a guarded path hook and does not automate native picker selection or dismissal.

Terminal keyword highlighting reads only xterm's parsed visible normal buffer and adds disposable foreground decorations. It does not parse raw ANSI output, alter terminal input/output, or persist text or matches. Rules use `re2js` and enforce limits on rule count, pattern length, compiled size, groups, line length, visible rows and matches. The CSP's inline-style exception supports xterm's generated stylesheet; it does not allow inline scripts or network sources.

## Third-party licensing and integrity

Every bundled or launched provider has `name`, `source`, `version`, `license`, `distribution-rights`, `hash/signature-check`, `update-policy`, `vulnerability-scan-status`. GPL/LGPL components require counsel/maintenance review before bundling; prefer explicit user-installed providers if unclear. Never copy comparison-product proprietary assets or internal scripts.

Optional Git for Windows Bash is user-installed and is not redistributed by the application. Opening a Bash terminal is an explicit user action; its normal `--login -i` startup files therefore run as part of launching the selected shell. P-36's app-managed PowerShell script is separate from Bash files and from the user's normal PowerShell `$PROFILE`: it remains stored but idle until its exact saved contents are previewed and explicitly sent to one running PowerShell tab. The current resolver checks the standard Bash install path but does not enforce a signature or hash; consult [WP-01's provider record](dependencies/WP-01.md) for the observed machine evidence and its limitation.

WP-11A's local shell catalog is a fixed catalog of PowerShell, cmd, Bash, and WSL shell actions. Its persisted visibility choice controls only whether a new-shell action appears in the command palette; launch continues through the existing typed local-terminal command and provider resolver.

WP-11C adds a fixed allowlist for Telnet, FTP/FTPS, serial, RDP, VNC, and the local TFTP server. Schema v10 preferences default these providers to enabled to preserve existing behavior. The renderer hides their new-launch actions after the persisted preference read succeeds; the main broker independently re-reads settings and denies new provider entry points when disabled, failing closed if settings cannot be read. If TFTP is disabled while its service is running, its manager action remains available so the user can stop it; folder selection and start controls stay disabled. Existing session I/O and close operations remain available for cleanup. No executable paths or third-party JavaScript can be registered through this setting; provider installation, update, provenance verification, and removal remain open work.

WP-11D adds a separate fixed availability list for PowerShell, cmd, Git Bash, and WSL. Schema v11 migrates existing profiles with every registered shell enabled. The renderer hides new-shell actions after a successful preference read and leaves saved definitions visible with a disabled reopen control when their shell is unavailable. The main broker rechecks persisted availability before `terminal.open` and WSL distribution discovery; a failed settings read blocks both. Shell input and close remain available to existing runtime sessions after a shell is disabled. If PowerShell is disabled, app startup skips the default PowerShell terminal and does not substitute another shell. This preference accepts only registered shell IDs and does not execute commands, change installed runtimes, or remove saved definitions.
