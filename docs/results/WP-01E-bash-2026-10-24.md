# WP-01E: Git Bash terminal

**Requirements:** F-002; partial progress toward P-02.
**Platform:** Windows 11 x64, Node 24.14.1, Electron 45.0.0, installed Git for Windows.
**Status:** Passed Windows build and Electron acceptance. P-02 remains partial; this does not establish release readiness.

## Delivered behavior

- The command palette opens an explicitly selected Bash terminal through the existing ConPTY utility worker.
- The worker resolves only `<Git>\\bin\\bash.exe` from standard machine-wide or per-user install roots. This uses the Git for Windows wrapper, does not consult arbitrary `PATH` entries, and cannot select the `System32\\bash.exe` WSL launcher.
- Bash is started as a login, interactive shell with `--login -i`; commands are not composed into a shell command line by the application.
- The shell type is accepted by the validated terminal contract and persisted session catalog. The saved-session list and terminal tabs identify Bash distinctly, and a missing Git for Windows installation produces a clear user-facing message.
- Ctrl+V and Ctrl+Shift+V require a trusted terminal key event, then a short-lived, one-use authorization bound to the terminal session. Clipboard text stays in the main process; NUL and text over 16,384 characters are rejected, and multiline paste requires a native confirmation before writing. Terminal input preserves per-session order across a pending paste, including writes already in flight and input received while authorization or confirmation is pending. Paste waits for the native decision and is cancelled if its renderer is destroyed.
- Acceptance covers a Bash-version command, Cyrillic/CJK BMP input by paste, terminal resize, saved-definition reopen and Ctrl+W closure of a Bash tab. A separate exploratory clipboard probe observed that Bash can render a supplementary emoji generated by the shell, but supplementary-character input pasted through the tested Git Bash/ConPTY path is replaced with U+FFFD; this observation is not asserted by the checked-in E2E test.
- No package dependency or bundled Git runtime was added.
- The acceptance machine's `bash.exe` reported Git for Windows `2.53.0.windows.2`, and Windows reported its Authenticode signature valid. The app does not enforce signature/hash verification or scan an external Git installation; update and provenance details are recorded in [WP-01 dependency review](../dependencies/WP-01.md).

## Validation

- `corepack pnpm typecheck` — passed.
- `corepack pnpm lint` — passed, including static import-boundary checks.
- `corepack pnpm test` — 109 passed, 0 failed, including gesture binding, multiline-paste confirmation, cancellation and input-order coverage.
- `corepack pnpm build` — passed on Windows x64; Vite emitted the existing renderer chunk-size advisory.
- Focused `corepack pnpm exec playwright test --grep "Git Bash"` — passed; the test covers clipboard paste, resize, shell commands, save/reopen and Ctrl+W tab closure.
- `corepack pnpm check` — passed on Windows x64: typecheck, lint/import boundaries, 109 unit and adapter tests, build, and all 12 Electron E2E tests. The E2E suite includes real PowerShell and Git Bash clipboard paste. Vite emitted its existing renderer chunk-size advisory.

## Limitations

Git for Windows must be installed in one of the standard roots for Bash to be available. Custom installation paths and WSL integration are not supported. The user manages updates; app-enforced signature/hash validation and vulnerability scanning of this external provider are not implemented. The exploratory observation about supplementary-character input remains a compatibility limitation to reproduce in a checked-in regression test; it leaves F-002 incomplete. Broader Unix-tool acceptance remains future work, so P-02 is partial. The Windows acceptance evidence comes from the configured Windows 11 x64 machine; it does not complete the full F-002 release gate or validate packaging.
