# WP-11E - WinGet as an optional tool-provider installer

**Date:** 2026-10-31
**Scope:** Assess whether Windows Package Manager can safely support an app-managed, fixed allowlist of optional command-line tools.
**Status:** Research plus an unverified fixed-package implementation candidate; no general provider catalog or lifecycle acceptance is approved by this finding.

## Findings

- WinGet is available on Windows 11 and modern Windows 10, but it may not be registered for a user until their first sign-in or may be absent. A provider integration therefore needs an explicit unavailable state and cannot be a prerequisite for app startup. [WinGet overview](https://learn.microsoft.com/en-us/windows/package-manager/winget/)
- WinGet supports exact package IDs, an explicit source, version/architecture selection, and a user-scope request. User scope is not guaranteed: WinGet may select machine scope when a package lacks a user installer, and some installers require elevation. A managed flow must allowlist packages independently proven to support user scope and fail closed rather than elevate or fall back to machine scope. [Install command](https://learn.microsoft.com/en-us/windows/package-manager/winget/install), [settings and scope](https://learn.microsoft.com/en-us/windows/package-manager/winget/settings), [administrator considerations](https://learn.microsoft.com/en-us/windows/package-manager/winget/)
- Community manifests require package publisher/license metadata and an `InstallerSha256`; MSIX manifests can additionally carry `SignatureSha256`. The documented SHA-256 comparison detects a changed installer relative to its manifest. It does not, by itself, establish publisher identity. MSIX packages are required to be signed, but the reviewed WinGet install documentation does not establish a general publisher-signer allowlist for EXE/MSI packages. [Manifest fields](https://github.com/microsoft/winget-cli/blob/master/doc/windows/package-manager/package/manifest.md), [repository validation](https://learn.microsoft.com/en-us/windows/package-manager/package/winget-validation), [MSIX signing](https://learn.microsoft.com/en-us/windows/msix/overview)
- WinGet's configured sources are mutable user/system configuration. Its defaults include the Microsoft Store and the WinGet Community Repository; source-management commands can add, edit, remove, and reset sources. The documentation says to use secure, trusted sources, and source agreements can be bypassed by command-line options. [Source command](https://learn.microsoft.com/en-us/windows/package-manager/winget/source)
- Install/upgrade/uninstall invoke package-controlled installer or uninstaller behavior. The CLI exposes options to suppress UI, accept package/source agreements, allow reboot, override installer arguments, and ignore a failed hash check. These options must not be passed by an app-managed flow; license terms and installer prompts need to remain visible to the user. [Install command](https://learn.microsoft.com/en-us/windows/package-manager/winget/install), [upgrade command](https://learn.microsoft.com/en-us/windows/package-manager/winget/upgrade), [uninstall command](https://learn.microsoft.com/en-us/windows/package-manager/winget/uninstall)

## Decision and remaining acceptance

WinGet is a possible execution adapter for a separately reviewed fixed catalog, not a trusted provider-discovery or signature-verification policy by itself. Before integration, each catalog entry still needs a named publisher/source, exact package ID, supported Windows versions and user-scope installer, version/update policy, license and redistribution disposition, signer/hash evidence, and an uninstall ownership policy. The app would need to show package identity and agreements before each explicit operation, pass only fixed arguments, prevent elevation/machine-scope fallback and automatic reboot, and never add or reset sources.

The initial research did not launch WinGet or install, update, or remove a package. A later read-only host check found Microsoft Desktop App Installer version `1.29.380.0`; the bounded `winget.exe --version` retry returned `v1.29.380`. No package was searched, installed, updated, or removed, and no package source was listed or changed. This establishes local command availability only, not a reviewed fixed catalog or provider lifecycle acceptance. F-009/P-21/P-31/P-37, F-017/F-024 and N-012 remain open as previously recorded. This finding does not mark any feature verified.

## Microsoft documentation follow-up - 2026-10-31

- Microsoft documents `winget source export winget` as returning the source name, URL, type, data/identifier, trust-level values, and explicit flag. Its documented default community source is `winget` at `https://cdn.winget.microsoft.com/cache`, type `Microsoft.PreIndexed.Package`, identifier `Microsoft.Winget.Source_8wekyb3d8bbwe`, trust values `Trusted` and `StoreOrigin`, and `Explicit: false`. The same source interface can add, edit, remove, reset, and export sources; a fixed package ID therefore does not prove that the user's named source still resolves to Microsoft's default. A managed operation would have to inspect and validate the exported source record without mutating source configuration. [Microsoft WinGet source command](https://learn.microsoft.com/en-us/windows/package-manager/winget/source)
- WinGet install accepts exact package IDs, an explicit source, exact versions, architecture, and scope filters. It also offers flags that bypass package/source agreements, suppress installer UI, allow reboots, override installer arguments, or ignore security-hash failures. An app-managed flow must use only fixed arguments and preserve user-visible agreements and installer interaction; it must never pass the bypass/override flags. [Microsoft WinGet install command](https://learn.microsoft.com/en-us/windows/package-manager/winget/install)
- `--scope user` is a selection constraint, not proof that an installer cannot request elevation. Microsoft's settings documentation says a user-scope requirement filters out nonmatching installers and can make installation fail when none apply; the WinGet overview also says some applications require elevation when invoked as a standard user, and installation fails if the user denies the elevation prompt. Each allowlisted package therefore still needs package-specific evidence that the selected installer is supported at user scope and that its actual behavior meets the no-unapproved-elevation policy. [Scope preferences and requirements](https://learn.microsoft.com/en-us/windows/package-manager/winget/settings#preferences-and-requirements-settings), [WinGet administrator considerations](https://learn.microsoft.com/en-us/windows/package-manager/winget/#administrator-considerations)
- These options improve the design constraints but do not establish a publisher-signed catalog, a general Authenticode publisher allowlist, package-specific scope/elevation acceptance, licensing disposition, or uninstall ownership. No catalog or installer integration is approved by this research update; F-009/P-21/P-31/P-37/F-017/F-024 and N-012 remain open. No WinGet package/source operation was executed.

## Dedicated-terminal safety correction - 2026-10-31

- The authored UI no longer targets an already-running PowerShell session. It opens a new `-NoProfile` local PowerShell terminal on explicit user action, enables package actions only for that newly returned session ID, and closes Settings after successful command submission so interactive prompts can be inspected in the dedicated tab. This avoids appending the fixed command to an existing user's partial command line.
- A Windows E2E case now covers dedicated-tab creation and action availability without installing, updating, or removing a package. It is authored only; no automated check or package operation ran. F-009/P-21/P-37 and the Phase 08 gate remain open.
- Microsoft documents `Remove-AppxPackage -Confirm` as a current-user removal command. The WinGet uninstall option list has no installer-type filter, so the candidate now checks the exact `Microsoft.PowerShell_8wekyb3d8bbwe` package family, Microsoft publisher, and x64 architecture before removal; install/update check the same registered identity after WinGet succeeds. This does not pre-verify the downloadable manifest or pin its signer thumbprint. See [Remove-AppxPackage](https://learn.microsoft.com/en-us/powershell/module/appx/remove-appxpackage), [WinGet uninstall options](https://learn.microsoft.com/en-us/windows/package-manager/winget/uninstall), and the [reviewed Microsoft.PowerShell 7.6.9 MSIX manifest](https://github.com/microsoft/winget-pkgs/blob/master/manifests/m/Microsoft/PowerShell/7.6.9.0/Microsoft.PowerShell.installer.yaml).
- The source predicate now requires the exact documented trust-level pair and `Explicit: false`; an extra trust value or changed explicit-source flag stops install/update. The focused builder assertions were updated but remain unrun.

## Pre-install MSIX identity and signer validation - 2026-10-31

- **Conclusion:** Windows can validate a downloaded PowerShell MSIX bundle before installation, but `winget download` alone is not a publisher/signer trust check. WinGet download can select exact ID, version, architecture, scope, installer type, and source; unless `--ignore-security-hash` is supplied, it checks the selected file against `InstallerSha256`. `SignatureSha256` is the SHA-256 of the package's inner `AppxSignature.p7x`, not a certificate thumbprint or publisher allowlist. [WinGet download](https://learn.microsoft.com/en-us/windows/package-manager/winget/download), [WinGet installer schema](https://github.com/microsoft/winget-pkgs/blob/master/doc/manifest/schema/1.12.0/installer.md)
- At this review, the current PowerShell manifest is `7.6.9.0` (released 2026-10-25). Its x64, x86, and arm64 MSIX entries all select the same `PowerShell-7.6.9.msixbundle`, with the same installer/signature hashes and `Microsoft.PowerShell_8wekyb3d8bbwe` family. Separate Wix MSI entries are machine-scope and `elevatesSelf`. The MSIX entries omit `Scope`, so the manifest itself does not declare a user-scope constraint. An exact x64 MSIX download selector excludes the MSI rows, but the chosen version should be pinned for a download-then-verify flow. [PowerShell 7.6.9 WinGet installer manifest](https://github.com/microsoft/winget-pkgs/blob/master/manifests/m/Microsoft/PowerShell/7.6.9.0/Microsoft.PowerShell.installer.yaml), [PowerShell 7.6.9 release](https://github.com/PowerShell/PowerShell/releases/tag/v7.6.9)
- **Read package identity before installation:** the Win32 AppxPackaging bundle reader can read the bundle manifest and enumerate payload packages; each package identity exposes name, publisher, package-family name, and architecture. Compare these values with the fixed catalog entry. `IAppxFactory::CreatePackageReader` validates package structure and manifest but explicitly does **not** validate the digital signature, so identity parsing and trust verification must be separate checks. [Bundle reader](https://learn.microsoft.com/en-us/windows/win32/api/appxpackaging/nn-appxpackaging-iappxbundlereader), [bundle manifest packages](https://learn.microsoft.com/en-us/windows/win32/api/appxpackaging/nf-appxpackaging-iappxbundlemanifestreader-getpackageinfoitems), [package identity API](https://learn.microsoft.com/en-us/windows/win32/api/appxpackaging/nn-appxpackaging-iappxmanifestpackageid), [package-reader signature limitation](https://learn.microsoft.com/en-us/windows/win32/api/appxpackaging/nf-appxpackaging-iappxfactory-createpackagereader)
- **Verify trust before installation:** Microsoft documents validating an app-package signature with Win32 `WinVerifyTrust` and `WINTRUST_ACTION_GENERIC_VERIFY_V2`; the Windows SDK SignTool is a command-line alternative, with Microsoft documenting `signtool verify /pa MyApp.msix`. Windows requires a signed package trusted by the device, and the manifest `Publisher` must exactly match the signer certificate subject. Windows deployment still revalidates when `Add-AppxPackage`/`PackageManager.AddPackageAsync` performs the actual install. [Programmatic package signature validation](https://learn.microsoft.com/en-us/windows/win32/appxpkg/how-to-programmatically-sign-a-package), [SignTool MSIX verification example](https://learn.microsoft.com/en-us/windows/apps/dev-tools/winapp-cli/usage), [MSIX signing and trust](https://learn.microsoft.com/en-us/windows/msix/package/signing-package-overview), [publisher-to-certificate match](https://learn.microsoft.com/en-us/windows/msix/msix-troubleshooting-guide)
- **.NET limit:** no single managed API was identified that validates the full MSIX package. `SignedCms` can verify a CMS signature and optionally validate its signer certificate chain, but that alone does not bind the manifest identity and Appx block map to the bundle contents. Prefer the Windows package/trust APIs (or SignTool) over a custom CMS parser. [SignedCms.CheckSignature](https://learn.microsoft.com/en-us/dotnet/api/system.security.cryptography.pkcs.signedcms.checksignature), [Appx package-reader behavior](https://learn.microsoft.com/en-us/windows/win32/api/appxpackaging/nf-appxpackaging-iappxfactory-createpackagereader)

**Limits at the research stage:** this verifies against the device's Windows trust policy; it does not pin an exact leaf certificate thumbprint or protect against compromised trusted publishers/roots. `SignatureSha256` pins only the signature-file bytes. The original proposed download/preflight/install sequence had a file-replacement window; the current candidate below holds the same file read-only through deployment. The earlier `--scope user` concern is superseded by current-user `Add-AppxPackage`. Windows-version coverage and actual package operation remain untested. No package was downloaded or installed, and no tests ran for this addendum.

## WP-11E pre-install signed-bundle implementation candidate - 2026-10-31

- Replaced direct WinGet install/upgrade with `winget download` for the fixed package ID, `winget` source, x64 architecture, and MSIX installer type. The command requires exactly one `.msixbundle`; it does not accept a WinGet-selected EXE/MSI or multiple package artifacts. Download-only operation leaves WinGet's source/package agreement prompts enabled. The WinGet CLI prompt implementation includes package agreements in installer-download-only mode; no agreement-acceptance flag is passed. [WinGet download](https://learn.microsoft.com/en-us/windows/package-manager/winget/download), [WinGet CLI prompt implementation](https://github.com/microsoft/winget-cli/blob/master/src/AppInstallerCLICore/Workflows/PromptFlow.cpp)
- Before deployment, the candidate checks `Get-AuthenticodeSignature` status `Valid`, exact signer subject, and the bounded `AppxMetadata/AppxBundleManifest.xml` identity (`Microsoft.PowerShell`, expected publisher, x64 application payload). XML DTD processing is prohibited. The bundle is opened read-only with write/delete sharing denied throughout signature/identity validation and `Add-AppxPackage -Confirm`, then its unique staging directory is removed in `finally`. [Get-AuthenticodeSignature](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.security/get-authenticodesignature), [Add-AppxPackage](https://learn.microsoft.com/en-us/powershell/module/appx/add-appxpackage)
- `Add-AppxPackage` installs a signed package into a user account, removing the earlier `winget --scope user` ambiguity for this MSIX. Windows also revalidates the package at deployment. The signature check uses the device's Windows trust policy and expected publisher subject; it does not pin a leaf certificate thumbprint or rule out a compromised trusted Microsoft signing chain. [App-package signature validation](https://learn.microsoft.com/en-us/windows/win32/appxpkg/how-to-programmatically-sign-a-package)
- WinGet resolves and downloads the selected latest version in one invocation; no separate version lookup is handed to a second download request. The signed bundle's manifest version is checked against the reviewed minimum `7.6.9.0` and the installed version to prevent older-version install/update. A compromised source could still replay an older, still-valid Microsoft-signed release at or above that floor; publisher/provenance and release-recency review remain open.
- The reviewed PowerShell 7.6.9 source `AppxManifest.xml` declares only a `TargetDeviceFamily` under `Dependencies` and no external `PackageDependency`; the bundle candidate therefore expects exactly one downloaded bundle and does not add unreviewed dependency packages. This remains tied to the reviewed version and must be checked again if the fixed package catalog changes. [PowerShell 7.6.9 AppxManifest.xml](https://github.com/PowerShell/PowerShell/blob/v7.6.9/assets/AppxManifest.xml)
- Command-builder assertions and the Settings E2E disclosure assertion were updated but not run. No package was downloaded, installed, updated, or removed. Windows signature behavior, current-user deployment, cleanup, interactive acceptance, package license/provenance, and the Phase 08 verification gate remain unverified; WP-11E/P-21/P-37 remain PARTIAL.

## Latest-stable version preflight - 2026-10-31

- GitHub documents `GET /repos/{owner}/{repo}/releases/latest` as returning the latest published full release, excluding drafts and prereleases; public repositories can use the endpoint without authentication. The implementation uses the fixed PowerShell repository endpoint, an explicit JSON Accept header, no credential, a 10-second cancellation deadline, disabled redirects, and a 64 KiB response bound. It accepts only a stable `vMAJOR.MINOR.PATCH` tag and fails closed on request, status, parse, or tag errors. [GitHub REST API: Get the latest release](https://docs.github.com/en/rest/releases/releases#get-the-latest-release)
- The command converts the three-part tag to the reviewed four-part MSIX version, passes that exact version to `winget download`, and compares it again with the signed bundle manifest before deployment. This addresses an older still-signed version being replayed by the source after a different latest version has been published. GitHub's release list showed `v7.6.9` as stable and `v7.7.0-rc.1` as prerelease at this checkpoint. [PowerShell releases](https://github.com/PowerShell/PowerShell/releases)
- The builder unit assertions and Settings E2E disclosure now cover the bounded endpoint and exact-version requirement; both are authored but unrun under the major-phase testing freeze. No package operation, source change, build, or automated verification ran. Release metadata, GitHub/TLS trust, publisher/license/provenance review, package-operation interoperability, and Phase 08 acceptance remain open; P-21/P-37/F-009/F-017/N-012 are not upgraded.

## MSIX processing size bound - 2026-10-31

- The current official PowerShell v7.6.9 release asset listing reports `PowerShell-7.6.9.msixbundle` at 336 MB. The command now opens the downloaded bundle with write/delete sharing denied and rejects an empty file or a locked file larger than 1 GiB before signature and archive inspection, leaving substantial headroom while bounding the bytes passed to those parsers. [Official v7.6.9 release assets](https://github.com/PowerShell/PowerShell/releases/expanded_assets/v7.6.9)
- This is a post-download processing bound: WinGet has already completed the transfer before the app can inspect the file length, so the limit does not cap temporary disk or network use during download. The command builder's bound assertion is authored but unrun. No package was downloaded or operated; Phase 08 remains unverified.

## Release asset digest binding - 2026-10-31

- GitHub's release asset API documents `size` and `digest` (`sha256:<hex>`) fields. The fixed release preflight now selects exactly one uploaded `PowerShell-<version>.msixbundle`, requires a valid SHA-256 and a size from 1 byte through 1 GiB, then compares the downloaded WinGet bundle's locked byte length and SHA-256 with those fields before signature and manifest parsing.
- The digest arrives in the same GitHub response as the release tag, so this detects disagreement between the chosen WinGet package and the described release asset; it does not independently authenticate GitHub release metadata or cap WinGet's transfer disk use. Authored command assertions and UI disclosure have not run. No API request or package operation occurred. Sources: [GitHub release asset schema](https://docs.github.com/en/rest/releases/assets?apiVersion=2026-03-10), [PowerShell v7.6.9 release asset and published hash](https://github.com/PowerShell/PowerShell/releases/expanded_assets/v7.6.9).

## Bundle-signature source verification - 2026-10-31

The pinned PowerShell 7.6.9 source shows `Get-AuthenticodeSignature` passes file paths to `SignatureHelper`, whose Windows fallback calls `WinVerifyTrust` with `WINTRUST_ACTION_GENERIC_VERIFY_V2`. Microsoft explicitly documents that action for app-package validation; MSIX documentation says a bundle's signature covers its contained packages. This supports the current `.msixbundle` preflight by source-backed inference, although the cmdlet documentation does not explicitly list bundle extensions. A real Windows `.msixbundle` check and package-operation acceptance remain required. [Source and limits](WP-11E-msix-signature-verification-2026-10-31.md)

## Bounded direct release download - 2026-10-31

- Source inspection found that rejecting an oversized WinGet result after download protects signature/archive parsing but does not bound transfer-time temporary disk writes. The implementation direction now streams the exact version-matched GitHub release asset to a unique file, enforces the API-declared byte limit before each write, requires the final byte count and incremental SHA-256 to match, and keeps the existing locked-file, Microsoft signature, package identity, confirmation, and cleanup checks. ADR-0065 supersedes ADR-0064; WinGet retrieval and source inspection are removed from the current candidate.
- The downloader disables automatic redirects, sends no credentials/cookies/default credentials, allows at most three HTTPS redirects only to `github.com` or `githubusercontent.com` hosts, uses a 60-minute cancellation token, and writes no more than the validated asset size (at most 1 GiB). GitHub's API docs provide `browser_download_url`, `size`, and `digest` metadata, and document the API's binary asset response as either 200 or 302. The project README identifies PowerShell as MIT-licensed. [GitHub release asset API](https://docs.github.com/en/rest/releases/assets?apiVersion=2026-03-10), [PowerShell project license statement](https://github.com/PowerShell/PowerShell#legal-and-licensing).
- The app UI now discloses the direct release route and links the upstream license statement; `Add-AppxPackage -Confirm` and removal confirmation remain visible. Assertions were updated in the command-builder, local-terminal, and Windows UI E2E sources. These are authored only: no tests, live API request, asset download, package operation, build, or Windows acceptance ran. GitHub API/TLS and Windows trust remain shared trust dependencies, and publisher/provenance review remains open; Phase 08 and P-21/P-37/F-009 remain PARTIAL.
